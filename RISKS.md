# Risk Register — vault-publisher

Companion to [`BRD.md`](BRD.md).

| ID | Risk | Likelihood | Impact | Mitigation / Status |
|---|---|---|---|---|
| RISK-1 | `hostPath` ties the Pod to one node. If that node goes down, the site is unavailable until the node recovers — there is no automatic failover. | Low (RPi5 nodes are stable) | High (complete service loss) | Accepted for current single-user homelab; revisit if a third node is added and HA becomes viable. |
| RISK-2 | During the first-ever run, `/site/current` doesn't exist until the first build completes. Caddy will 404 during this window. | Certain (one-time, first deploy only) | Low (brief, known window) | Document as expected behavior. Liveness probe should not use `/site/current/index.html` until after first build. |
| RISK-3 | A quartz upstream release may introduce a breaking change to `quartz.config.yaml` format or CLI flags, silently breaking builds. | Low | Medium | Pin quartz to a specific version in `package.json`; upgrade deliberately. CI build validates the image. |
| RISK-4 | SSH deploy key exposure. A misconfigured Secret volume (`0644` instead of `0400`) causes SSH to silently reject the key, not a security leak — but a misconfigured RBAC that grants broad Secret read access would expose the key to other cluster workloads. Since the git-sync sidecar architecture (BRD §9.2), the key is mounted only into the git-sync container — the daemon never has it (NFR-SEC-5), narrowing which container's compromise would expose it. | Low | High (scoped to git-sync container only) | Mount with `defaultMode: 0400` (documented hard rule). Scope RBAC to the namespace. |
| RISK-5 | A long-running quartz build on RPi5 may time out, OOM-kill, or spike CPU enough to affect other workloads on the same node. | Medium (large vault) | Medium | Set resource `limits.memory` on the builder container. Monitor with `kubectl top`. If chronic, add a build concurrency lock. |
| RISK-6 | Two compounding `rename(2)` failure modes, both confirmed by direct test against a real container/bind-mount: (1) `rename(2)` refuses to rename a directory that is itself an active mount point (`EBUSY`), which `/site` always is under `hostPath` — this made every promotion fail, every time, with the site never publishing at all (issue #4). Fixed by keeping `current`/`next`/`old` as sibling subdirectories under `/site` rather than mount-point paths. (2) Separately, `rename(2)` still refuses to replace a non-empty directory (`ENOTEMPTY`), so a single `rename(next, current)` only works on the very first build; every later promotion needs two renames (`current` → `old`, then `next` → `current`), with a brief gap where `current` doesn't exist. | Certain (every build) | Medium (a request in the gap gets a transient 404, not corrupt content) | (1) verified fixed by an end-to-end Docker run against a real `git-sync` sidecar — see `next-steps.md`. (2) Two-step rename in `src/build.ts`; `old` cleaned up after. Caddy retries/reconnects on the next request — no partially-written content is ever served, only an occasional momentary 404. |
| RISK-7 | The vault git repo becomes unreachable (network issue, SSH key rotation, repo moved). Since BRD §9.2, this is git-sync's failure mode, not the daemon's — git-sync retries on its own backoff and the daemon simply never sees `/vault/current` change, so it cannot rebuild. | Low | Low (last build continues to be served) | Rely on git-sync's own retry/backoff and logging. Add a Gatus check for the site so staleness is visible. |
| RISK-8 | git-sync is a new third-party image dependency with its own release cadence. A breaking change to its flags, `--root`/`--link` layout, or symlink-update semantics could silently stall syncs — `/vault/current` stops advancing but nothing crashes, so the daemon keeps serving a stale build indefinitely without an error. | Low | Medium | Pin the git-sync image tag explicitly (no `:latest`). Alert on `/vault/current`'s mtime/target going stale beyond a few `VAULT_SYNC_PERIOD`s, not just on git-sync container crashes. |
| RISK-9 | `readVaultCurrentRef` (`src/vault.ts`) resolves `/vault/current` to a concrete `rev-<sha>` directory once per poll cycle and pins the build to it (FR-BUILD-7), so a symlink retarget mid-build no longer causes a torn read. But if git-sync garbage-collects that specific rev directory *while a slow build is still reading it* (RISK-5), the build can still fail with an I/O error partway through — this repo's code can pin to a path, but can't control how long git-sync keeps old revs around. | Low (git-sync typically retains a few prior revs) | Medium (a build failure, not corrupt output — FR-BUILD-3 leaves `/site/current` untouched either way) | When configuring the git-sync sidecar, keep its rev-retention window comfortably longer than the slowest expected build (see RISK-5's build-time monitoring). No code-side mitigation is possible — flag this in K8s deployment docs when they're written (`next-steps.md`). |
| RISK-10 | FR-BUILD-7's change detection compares resolved `/vault/current` *paths*, not git commit SHAs directly — a path-identity proxy for content-identity, replacing v0.2's direct SHA comparison. This assumes git-sync names its rev directories deterministically by content. | Low | Low (spurious rebuilds of identical content on every restart, not incorrect output or staleness) | Confirmed against the pinned image (`registry.k8s.io/git-sync/git-sync:v4.2.4`) via the Verify step: worktrees are named `.worktrees/<commit-sha>`, deterministic by content. Closed. |
